Tick & unit math

System architecture — reference doc

Power Grid

A tick-driven power-grid simulation split into five Spring Boot services plus a shared data layer and a React dashboard — seven services in total. Every five real seconds is one simulated tick; 288 ticks make one simulated day. Nothing here shares a database table or a compiled class across a service boundary — every cross-service contract is either a Kafka event or a REST call, by deliberate choice.

01 — how the seven fit together

Data flow

Grid owns simulated time and broadcasts the tick. Producer and Customer each react to it independently — supply and demand are computed in parallel, never waiting on each other. Distributor merges the two into a balance and, separately, tracks a per-zone capacity ceiling. Billing reacts to the same demand stream Distributor does, as its own independent Kafka consumer, and separately mirrors Distributor's capacity config to price overage.

Kafka topic (async, at-least-once) REST / JDBC (sync)

02 — the paradigms

Architectural paradigms

Not one style stacked five times — each service picks the paradigm its own job actually needs, inside one consistent system-level shape.

SYSTEM-WIDE

Microservices, database-per-service

Five independently deployable Spring Boot processes. No shared jar, no shared schema — each owns its own Postgres schema or Redis key namespace, reachable by no one else's JPA.

SYSTEM-WIDE

Event-driven, tick-as-heartbeat

Grid's grid.tick is the system's pulse. Producer and Customer both react to it independently and in parallel — there is no orchestrator waiting for both.

PER-SERVICE

Hexagonal / ports & adapters

Customer, Distributor, Billing and Producer each keep a framework-free core (an interface — the "port" — plus plain Java) with Kafka/JPA/Redis code living only in adapter classes at the edge.

CUSTOMER ONLY

Reactive streams

Customer is the one WebFlux + reactive-Redis service — its own zone/unit CRUD is naturally I/O-bound and non-blocking; every other service is plain blocking WebMVC.

FRONTEND

Component + server-cache view

React Flow renders the live topology; TanStack Query owns every poll, cache and invalidation — the component tree never calls fetch directly.

DATABASE

Polyglot persistence

Postgres for anything relational and billed (Producer, Distributor, Billing); Redis for anything that only needs current state, fast (Customer, Grid's clock).

03 — the principles

Design principles applied everywhere

The rules that shaped individual decisions across the whole system, not just one service.

Independent deployability over DRY

A wire event like ZoneDemandEvent is copied field-for-field into every service that consumes it, rather than shared from one library.

Trade-off, made on purpose: a shared jar would couple every service's release train together.

Idempotency at every trust boundary

Kafka is at-least-once. Every listener that causes a side effect sits behind a DB uniqueness check — (zone_id, tick_number) on billing and distribution records.

One atomic method beats two clean ports

BillingLedger.apply(...) is one method, not a "record" port plus a "debit" port — because the two must commit or fail together, and two ports can't guarantee that.

A side effect never costs its sibling

Logging and publishing after a merge are independent, guarded calls — a broker outage still lets the DB write land, and vice versa.

No abstraction before a second caller

Two output ports, not three. No repository method nobody calls yet. Every interface earns its place from an actual current need.

Simulated time is its own currency

Retention, billing cycles and rollups are counted in ticks, not wall-clock durations — a paused simulation must not silently lose or gain history.

Structural, not compiled, contracts

A cross-service event's "type safety" is a documented field order everyone agrees to, enforced by nothing but code review and a comment pointing at the canonical copy.

Never let one bad record wedge a partition

Every @KafkaListener body is wrapped try/catch, logged and swallowed — the default error handler retries forever otherwise, stalling every event behind it.

04 — the patterns

Design patterns in play

Ports & Adapters

A use-case service depends on a small interface; a Jpa* or Kafka* class implements it. The use case itself never imports Spring Data or Spring Kafka.

Strategy

Producer's GenerationStrategy — one implementation per PlantType (Thermal/Solar/Wind), selected by the plant being ticked.

Publisher/Subscriber

Every cross-service data flow is Kafka topic → one or more independent consumer groups. Billing and Distributor both read customer.demand without knowing about each other.

Repository

Spring Data JPA interfaces per aggregate, plus hand-written native queries where the aggregation has to run inside Postgres, not the JVM (the rollup jobs).

Idempotent Consumer

A unique DB constraint turns a Kafka redelivery into a checked no-op instead of a double charge or a doubled record.

Ledger (event-sourced balance)

Wallet holds current balance; WalletTransaction is an insert-only log of every movement that produced it — the same split BillingRecord (why) and the transaction (what moved) make explicit.

Rollup / compaction

Raw per-tick rows outside a retention window are aggregated into one row per bucket and the raw rows dropped — used by Producer (real-time minute buckets) and, since this session, Distributor and Billing (simulated-day buckets).

Cache mirror

Billing's ZoneCapacityCache is a read-only, in-memory mirror of Distributor's own config, kept in sync by consuming Distributor's own config-change topic — config replication without a shared table.

DTO / wire record

Every request, response and Kafka payload is its own record — never the JPA entity itself crossing a boundary.

Facade (frontend)

Each *Queries.js module is the only thing a component ever imports — it hides fetch, polling interval and cache-key details behind one hook per operation.

05 — the conventions

Rules used the same way, every time

The unglamorous, load-bearing consistency — the reason any one service reads like the others.

UTC pinned in main()
Every service sets TimeZone.setDefault(UTC) before SpringApplication.run — pgjdbc sends the JVM's default zone during the handshake, and Postgres 18 rejects what Windows resolves India to.
One schema per service
ddl-auto: update + default_schema + create-database-schemas: true — every JPA-backed service owns exactly one Postgres schema, named after itself.
Defensive Kafka deserialization
ErrorHandlingDeserializer wrapping JacksonJsonDeserializer(Type.class, false) everywhere — a malformed record logs and gets skipped, never wedges the partition.
autostart flags on every listener
Every @KafkaListener is gated by a boolean property, off in tests — loading a Spring context never quietly consumes from a real broker.
One ApiExceptionHandler per service
A domain exception maps to one HTTP status, consistently — 404 not-found, 402 insufficient funds, 400 failed validation — via @RestControllerAdvice.
204 on delete, always
Every @DeleteMapping that returns nothing is explicitly @ResponseStatus(NO_CONTENT) — a bare void silently serves 200 instead, which the frontend's fetch wrapper does not expect.
double, not BigDecimal
Every physical and monetary quantity — MW, kW, ₹ — is a double, for consistency with the rest of the codebase, a deliberate, documented trade-off against textbook money-as-BigDecimal.
Jakarta Validation at every write boundary
@NotBlank / @Positive on request records, @Valid on the controller parameter — never a hand-rolled null check.
One tick, everywhere, forever
288 ticks = 1 simulated day = 24 real minutes; 1 tick = 5 real seconds = 5 simulated minutes. Grid's SimulationClock is canonical; every other service's copy must stay numerically identical to it.

06 — service by service

The seven services

Ordered by where data originates — time, then supply and demand in parallel, then the merge, then money, then the two services that aren't Spring Boot at all. Each service below carries two tables now: Mini-modules, the package-level grouping, and — inside the collapsed Atomic units toggle — every class, interface, record or enum in it, one line each, down to the smallest thing that still has exactly one job. A couple of near-identical sibling DTOs (a create body and an edit body for the same entity) share one row to stay scannable; every other row is one file.
